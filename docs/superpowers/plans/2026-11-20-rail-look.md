# The Rail Look Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On a text VT, PID 1 draws the boot rail as a styled status display (banner, track, colour chips, finish line, runtime and shutdown lines) in its own `schema-16x32` font and neon palette, while serial consoles, log-file stdout and `rail.log` stay byte-identical.

**Architecture:** A pure renderer (`rail.c`) turns (event, service snapshot, phase) into a styled line; a small state machine in the same file decides *whether* and *when* to show it (SPAWN delay, first ONLINE, settle, finish buckets). `rail_console.c` owns every console ioctl (mode test, transactional font load, palette save/apply/restore) behind an injectable ioctl function so each failure is testable. PID 1 wires it in through a `service_log` hook, the existing `engine_hooks` (`wake_due`, `loop_tail`, `shut_log`) and one new hook for shutdown outcomes. `rail.c`/`rail_console.c` link only into `schema-init`; `schema-user` and the tests that link `service.c` are untouched.

**Tech Stack:** C99 (`-D_GNU_SOURCE`), Linux VT ioctls (`KDGETMODE`, `KDFONTOP`, `GIO/PIO_UNIMAP`, `PIO_UNIMAPCLR`, `GIO/PIO_CMAP`, `FBIOGET_VSCREENINFO`), Python 3 build tools (BDF → PSF2 → C array), existing shell/C test style in `tests/`.

**Spec:** `docs/superpowers/specs/2026-11-20-rail-look-design.md`

## Global Constraints

- Styled output only when `ioctl(fd, KDGETMODE)` succeeds **and** returns `KD_TEXT`, and not switched off (`schema.rail=plain` on the cmdline, or the word `plain` in `/etc/schema-init/rail`).
- `rail.log`, the recorder, and every non-VT stdout get today's exact line from `service_log` — byte-identical (golden test).
- Font/palette work never blocks, never retries, never fails a boot; any failure → plain text + one rail.log note.
- Font: `schema-16x32`, exactly **256** glyphs, 16×32, PSF2 with Unicode table, built from Spleen 16×32 (BSD-2-Clause; `fonts/LICENSE.spleen` kept and shipped).
- Font skipped when: `/dev/fb0` missing or `xres < 1280`; `/etc/vconsole.conf` `FONT=` (Debian `/etc/default/console-setup` `FONTFACE=`) names anything other than empty/`eurlatgr`/`schema-16x32`; `nofont` in `/etc/schema-init/rail`; `schema.rail_font=off`.
- Palette (slot: RGB hex): 0 `07060b`, 1 `ff4d5e`, 2 `3ddc84`, 3 `ffd23f`, 4 `4da3ff`, 5 `c46cff`, 6 `3fe0ff`, 7 `c8c8d0`, 8 `5c5870`, 9 `ff8090`, 10 `7dffb0`, 11 `ffe680`, 12 `80c0ff`, 13 `e29bff`, 14 `90f0ff`, 15 `ececf2`.
- Original palette persisted to `/run/schema-init/console-orig` (48 bytes, 0600, atomic) on first apply; a re-exec'd PID 1 reads it and never re-saves; shutdown restores it through `/dev/tty0` regardless of shutdown styling. Font is not restored at shutdown (only rolled back on a failed load).
- Re-exec'd PID 1: never prints banner or finish line; all lines runtime shape. No change to `reexec_state.h`.
- Name column: 17 terminal columns; font mode truncation `…`, fallback `~`; code points without a glyph (font mode) or any non-ASCII byte (fallback) shown as `?`.
- Fallback alphabet is strictly ASCII for every byte the renderer emits.
- Settle armed only after the first engine loop tail; finish line at most once per boot; 120 s cap prints `rail still starting after 120s` (yellow); SPAWN shown only if still starting 2 s after spawn.
- Guiding rule: never claim healthy / settled / restored unless the state supports it.

## Review Focus

1. A boot where PID 1's stdout is `/dev/console` backed by **tty0 + ttyS0** — expect styled on the VT side only if KDGETMODE on fd 1 says KD_TEXT; serial gets plain; nothing garbled. → Task 5 QEMU run with both consoles.
2. **Very fast boots** where a service is spawned and ready in the same engine tick — expect one ONLINE line, no SPAWN, no duplicate ONLINE on a later `promote`. → Task 3 test `fast_ready_single_line`.
3. A service **name of exactly 17 columns** and one of 40 bytes of UTF-8 — expect no misaligned chip column. → Task 2 test `name_widths`.
4. **Reload / `schema-ctl add` after settle** adding services — expect runtime lines, finish buckets not recomputed, no crash from `svc_count` growing. → Task 3 test `services_added_after_settle`.
5. **Shutdown during boot** (before settle) — expect the HALT banner and outcomes, no finish line printed afterwards. → Task 5 test `shutdown_before_settle`.
